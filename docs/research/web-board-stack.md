# Web/board stack for a fast opening-drill loop

Research ticket: [03-python-web-board-stack](../../.scratch/chessop/issues/03-python-web-board-stack.md). Date: 2026-09-11. Downloaded sources live in [`refs/stack/`](../../refs/stack/) (index in [`refs/README.md`](../../refs/README.md)).

The play loop we need: learner drags/clicks a move, the app replies instantly, a wrong move flashes, the next round starts at once. The question is which Python stack gets there with the least friction.

## Summary

1. Every Python-first framework (NiceGUI, Reflex, Streamlit, Panel) and every HTMX flavour puts a network round trip between the learner's drop and the board's reaction. Only a JS board with client-side chess logic can flash a wrong move with zero server latency.
2. The cleanest fit is **FastAPI (or Flask) + a JS board + chess.js in the browser**, with the server owning the repertoire tree and sampling and answering one small JSON message per learner move over a WebSocket (or fetch). Per-move work server-side is microseconds; the visible cost is board animation, which every library lets you shorten or disable.
3. Board choice is a licence decision more than a feature one: **cm-chessboard** (MIT, 8.14.0 on 2026-09-01, zero deps, SVG) is the safe default; **chessground** (Lichess, GPL-3.0-or-later, 10.1.1 on 2026-03-27) is the most polished but the README says a website using it "must release your source code". chessboard.js (MIT) has had one release since 2019 and needs jQuery; chessboard2 (ISC) has been "in progress" since 2023 with no release since.
4. **NiceGUI** is the strongest Python-first option: FastAPI + socket.io, per-client `@ui.page` state, and a documented path for custom Vue/JS components, so the board can stay client-side while Python receives one event per move. Reflex can wrap React boards but its own maintainers say event handlers cannot return a value, so snap-back logic must live in JS anyway. Streamlit reruns the script per interaction (fragments soften it) and its only chess component is from 2021. Panel's JSComponent works but drags in the Bokeh/Tornado server for no gain.
5. **python-chess `chess.svg.board`** renders a 400 px board in ~0.7 ms (31 KB SVG, 5.4 KB gzipped) on this machine, so HTMX/SSR is fast enough server-side; the drag-and-drop input and the wrong-move flash are what SSR cannot do without hand-rolled JS.
6. Deployment: all options are one process. Single-user local use is trivial for all; multi-user hosting is simplest with FastAPI+JS or NiceGUI (one async worker), hardest with Reflex (two ports, Redis for multi-worker) and Streamlit (a full session per tab).
7. Hedged recommendation: FastAPI + cm-chessboard + chess.js, WebSocket per session, python-chess server-side; fall back to NiceGUI wrapping the same JS board if the rest of the UI (progress views, settings) would otherwise cost more than the board.

## Option A: FastAPI/Flask + a JS board

### How a move round-trips

The board library handles drag/click and calls a callback with `(from, to)`. With chess.js (BSD-2-Clause, 1.4.0, 2025-06-14 [npm]) in the browser, legality is decided locally with no network hop; the official chessground examples do exactly this, computing `dests` from chess.js and swapping `movable.color` after each move (`playOtherSide`, `aiPlay` in [chessground-examples/util.ts](../../refs/stack/chessground-examples-util.ts)). For the trainer, "legal" is not enough: the app must also know whether the move is *in the repertoire* and what the sampled reply is. Two designs:

- **Server decides per move**: browser sends `{fen|uci}` over a WebSocket (FastAPI: `@app.websocket`, `receive_text`/`send_text` loop [FastAPI docs]) or a `fetch` POST; server checks the repertoire, samples the reply, returns `{ok, reply_uci, next_dests}`; browser animates. One round trip per learner move (LAN/localhost: ~1 ms; hosted: one RTT, typically 20-100 ms).
- **Client holds the current branch**: server ships the sub-tree (or the next N plies with weights) when a round starts; wrong-move flash and reply are decided in JS with zero latency; the result is reported back once per round. More client code, but the loop is as fast as the board animation.

Either way the server's own work is negligible: on this machine python-chess does `board.fen()` in 0.016 ms, `list(board.legal_moves)` in 0.015 ms, `copy()+push_san` in 0.009 ms (measured, python-chess 1.11.2 on Python 3.13).

### Board libraries

**chessground** (Lichess). npm `@lichess-org/chessground` 10.1.1 released 2026-03-27 (the legacy unscoped `chessground` package stopped at 9.2.1, 2025-05-15); repo pushed 2026-09-10, 1,367 stars, 34 open issues [npm, GitHub API]. Licence GPL-3.0-or-later; README: "When you use Chessground for your website, your combined work may be distributed only under the GPL. You must release your source code to the users of your website." Features per README: custom DOM diff ("Fast. Uses a custom DOM diff algorithm"), 10 K gzipped, no dependencies, SVG arrows/circles, full touch support, click and drag input, premoves, animation, "No chess logic inside". Input contract from [config.ts](../../refs/stack/chessground-config.ts): `movable.dests` (a `Map` of legal destinations), `movable.free`, `movable.events.after(orig, dest, metadata)`; `animation.duration` (values under 70 ms disable animation). API from [api.ts](../../refs/stack/chessground-api.ts): `set(config)`, `move(orig, dest)`, `getFen()`, `setShapes()`, `cancelMove()`, `playPremove()`. Wrong-move flash: since `dests` gates what can be dropped, an off-repertoire but legal move is accepted by the board and must be reverted by calling `set({fen})` or by restricting `dests` to repertoire moves only (which hides the wrong answer from the learner; a design choice, see Implications). Companion logic library from Lichess is chessops (0.15.1, 2026-07-12, also GPL-3.0-or-later [npm]); chess.js works equally well.

**cm-chessboard**. npm 8.14.0 released 2026-09-01; repo pushed the same day; 303 stars, 0 open issues, 485 published versions since 2017 [npm, GitHub API]. MIT. README: "lightweight, ES6 module based, responsive, SVG rendered and without dependencies"; in production on chessmail.eu/de. Input: `enableMoveInput(handler, color)` fires `moveInputStarted`, `validateMoveInput` (return `false` to cancel; "The validator runs once at most per sequence of actions that describe a move ... so side effects like updating game position state or triggering sounds can run here"), `moveInputCanceled`, `moveInputFinished`, `movingOverSquare`. `setPosition(fen, animated)`, `movePiece(from, to, animated)` return Promises resolved after animation; `animationDuration` default 300 ms, "Disable all animations with 0". Extensions: Markers, Arrows, PromotionDialog, Accessibility. Available from jsDelivr CDN as an ES module, so no bundler is needed. Because `validateMoveInput` is a synchronous return, an in-repertoire check must be answerable in JS (client-held branch) or the move must be accepted and then reverted after the server answers.

**chessboard.js**. npm `@chrisoakman/chessboardjs` 1.0.0 released 2019-06-11, the only version on npm; repo pushed 2024-04-17, 2,132 stars, 109 open issues [npm, GitHub API]. MIT. Depends on jQuery (README says 3.4.1+, docs page says 1.8.3+). README "Project Status (Dec 2022): I am currently focusing my efforts on chessboard2". Input: `draggable: true`, `onDragStart` (return `false` to prevent), `onDrop(source, target, piece, newPos, oldPos, orientation)` returning `'snapback'` to bounce the piece; `moveSpeed` 200 ms default, `snapbackSpeed` 50 ms [docs]. Mature but frozen; the snapback idiom is exactly the "wrong move flashes" behaviour, but it is synchronous, so the same client-side-knowledge constraint applies.

**chessboard2**. npm `@chrisoakman/chessboard2` 0.5.0 released 2023-05-29 (four versions total); repo pushed 2024-02-17, 113 stars, 46 open issues [npm, GitHub API]. ISC. Written in ClojureScript, no dependencies, "better mobile support". README status "April 2023: Development in progress. Getting close to an initial v2 release. Pretty usable for most projects"; the TODO-before-go-live list is still open and no v2.0.0 has shipped. Not a safe base for new work.

### Deployment and users

One Python process (uvicorn for FastAPI; Flask dev server or gunicorn) serving static HTML/JS plus one WebSocket/HTTP endpoint. FastAPI 0.141.1 (2026-07-29), Flask 3.1.3 (2026-02-19) [PyPI]. Flask needs Flask-SocketIO or `flask-sock` for WebSockets; Flask-SocketIO's docs say the `threading` mode has "full support of long-polling and WebSocket transports", eventlet "is not actively maintained anymore", and "If using multiple processes, a message queue service must be configured" [Flask-SocketIO intro]. FastAPI's async WebSocket is native and needs nothing extra. Single-user: run locally, open a browser. Multi-user: sessions keyed by cookie/token; one async worker handles many idle boards because the per-move work is microseconds.

## Option B: NiceGUI

NiceGUI 3.16.0 released 2026-08-12, MIT, repo pushed 2026-09-11, 16,196 stars [PyPI, GitHub API]. README architecture section: "Tech stack: Python/FastAPI backend, Vue/Quasar frontend, socket.io for communication"; "Single worker: Uses one uvicorn worker (thanks to full async support, no multi-process synchronization needed)"; "Real-time communication: WebSocket connection is established after initial page load"; "User interactions: All UI events are sent to backend and invoke Python functions"; "Outbox: Accumulates UI updates and sends them in batches to the client".

Move round trip: a board embedded as a custom Vue/JS component (the repo ships an [example](../../refs/stack/nicegui-custom-vue-component-README.md) where a JS component "emits an event with the new value" and Python calls its methods) sends one socket.io event per move; Python replies by calling a component method (`run_method`) which the outbox batches to the client. `.on()` handlers can be async, accept a `throttle` in seconds, can restrict which event attributes are transferred ("This can reduce the amount of data that needs to be transferred"), and `js_handler` lets an event be handled "without sending any data to the server" [NiceGUI generic events]. So the same two designs as Option A apply: server decides per move (one socket.io round trip) or the JS component holds the branch.

Multi-user: "Each user accessing the given route will see a new instance of the page. This means it is private to the user and not shared with others" (`@ui.page`) [NiceGUI page docs]; `ui.storage.user` for persistence. Deployment: `python main.py`, `ui.run(native=True)` for a desktop window, official Docker image `zauberzeug/nicegui`, `nicegui-pack` for a PyInstaller binary; a custom FastAPI app can mount NiceGUI [NiceGUI config & deployment]. Friction: you still write the board glue in JS (Vue component wrapping cm-chessboard or chessground), and NiceGUI's Vue-2 component model adds a layer to debug; in return the rest of the UI (progress lists, settings, dialogs) is pure Python.

## Option C: Reflex

Reflex 0.9.10.post2 released 2026-09-08, Apache-2.0, 28,881 stars, 370 open issues [PyPI, GitHub API]. Architecture blog: "Reflex apps compile down to a single-page Next.js app" on port 3000; "Reflex uses a FastAPI server (by default on port 8000) that the frontend connects to through a websocket"; "all the state and logic stays in Python and is run on the server"; "Reflex uses WebSockets to send events from the frontend to the backend, and to send state updates from the backend to the frontend"; per-client token maps to a state instance; "In production we use Redis as our state manager".

Move round trip: wrap a React board (react-chessboard 5.12.1, MIT, 2026-08-16 [npm]) via the wrapping-React API (`library`, `tag`, event triggers). But the react-chessboard `onDrop` contract expects a boolean return to accept/snap back, and a Reflex community thread (Oct 2024, forum.reflex.dev, now redirected to GitHub Discussions) records the maintainers' answer that there is no notion of returning a value from an event handler and that significant changes to Reflex would be needed; the workaround is to do that logic in JavaScript. So the wrong-move flash cannot be a Python decision on the drop event; it must be client-side JS or a two-step (accept, then Python pushes a corrected FEN via a state delta, one WebSocket RTT later).

Deployment: two ports (3000 static frontend, 8000 backend) or an exported static build behind a reverse proxy; `api_url` must be reachable by the browser; Docker example provided; Node is needed at build time [Reflex self-hosting]. Multi-user is built in but multi-worker needs Redis. Heaviest toolchain of the options.

## Option D: Streamlit

Streamlit 1.63.0 released 2026-09-01, Apache-2.0, 45,732 stars [PyPI, GitHub API]. Execution model: "any time something must be updated on the screen, Streamlit reruns your entire Python script from top to bottom" [main concepts]; since 1.37 `@st.fragment` makes "only the fragment reruns instead of the full script" when a widget inside it changes [fragments]. Transport: "built on the Tornado web framework, which uses WebSockets to maintain a persistent, two-way communication channel"; "Each browser tab or window creates its own WebSocket connection, resulting in a separate session" [architecture].

Move round trip: a bidirectional custom component renders "via an iframe tag"; `Streamlit.setComponentValue()` sends a value to Python "which then re-executes the Python script from top to bottom" [components intro]. So every learner move = iframe postMessage + WebSocket + (fragment) rerun + re-render of the component with new args, and the iframe reloads its state unless carefully keyed. The only published chess component, `stchess` 0.0.1 (2021-05-28, TheoLvs/streamlit-chess, 7 stars, last push 2023-06-30), wraps chessboardjsx and has not been maintained. Deployment is one command and Community Cloud is free, but the rerun model fights the "next round starts immediately" requirement.

## Option E: Panel (HoloViz)

Panel 1.9.4 released 2026-08-17, BSD-3-Clause, 5,771 stars [PyPI, GitHub API]. Transport: "The Bokeh server is built on Tornado, which handles all of the communication between the browser and the backend. Whenever a user accesses the app or dashboard in a browser a new session" is created [Panel server how-to]. Custom board: `JSComponent` (introduced June 2024 as successor to `ReactiveHTML`) takes an `_esm` module exporting `render({model, el})`, supports `_importmap` so "JavaScript dependencies can be directly imported via URLs, such as those from esm.sh", syncs `param` values both ways (`model.on('value', cb)`), and sends events to Python with `model.send_event(name, DOMEvent)` handled by `_handle_<name>` or `.on_event` [Panel JSComponent]. Functionally equivalent to NiceGUI's custom component with an ESM-first import story, but the Bokeh document/session machinery and Tornado server are heavier than needed for a one-board app, and Panel's idioms are dashboard-oriented. Multi-user: session per connection, `--num-procs` for scaling.

## Option F: HTMX + server-rendered SVG (python-chess)

htmx 2.0.10 released 2026-04-21, licence Zero-Clause BSD (LICENSE file), "~16k min.gz'd, dependency-free" [htmx home]. Model: any element issues an HTTP request on an event and the response HTML replaces a target (`hx-trigger`, `hx-target`, `hx-swap`); WebSockets via the `ws` extension (`ws-connect`, `ws-send`; messages are "swapped in by the id property, using the same logic as Out of Band Swaps") [htmx docs, ws extension].

python-chess 1.11.2 released 2025-02-25, GPL-3.0+ [PyPI]. `chess.svg.board(board, *, orientation, lastmove, check, arrows, fill, squares, size, coordinates, colors, borders, style)` returns an SVG string; `fill` maps squares to colours and `arrows` draws arrows, which covers "flash the wrong square" and "show the book move" [python-chess svg docs]. It is built with `xml.etree.ElementTree` and inlines piece `<defs>` [svg.py]. Measured on this machine (Python 3.13.13, python-chess 1.11.2, 300 iterations): 0.69 ms per 400 px board with `lastmove`; 0.49 ms without coordinates; 0.72 ms with `fill` + `arrow` + `check`. Output is 31,320 bytes, 5,446 bytes gzipped. So rendering is not the bottleneck: a server can re-render a board per move at thousands per second.

The problem is input. A static SVG has no drag-and-drop; the minimum viable input is two clicks (from-square, to-square) each an `hx-post` (or one click if the from-square is chosen client-side with a few lines of JS), then a swap of the whole 31 KB board. Each learner move therefore costs one HTTP round trip *before* any feedback, and there is no animation unless you add it. `hx-swap="morph"` or the ws extension reduce flicker but not latency. Fine for a local single-user tool where RTT is ~1 ms; on a hosted deployment the learner sees RTT-sized lag on every click, and the "wrong move flashes" requires a second render. Deployment is the simplest of all (one Python process, one template, no npm); multi-user is a normal session cookie.

## Implications for the trainer

- The "learner moves, app replies instantly, wrong move flashes" loop is a client-side loop. Whatever framework surrounds it, the board and the accept/reject decision should run in the browser, which means a JS board plus either chess.js or a server-supplied `dests` map. Every Python-first framework still needs that JS component written; none removes it.
- Two loop shapes fall out, and the choice belongs with the sampling-rule and leaving-the-book tickets: (a) **server decides per move** (simplest state model; one RTT per move; fine locally, noticeable when hosted), or (b) **client holds the sampled branch** (server sends the current sub-tree with the opponent's sampled replies when a round starts; the browser plays the whole line with zero latency and posts one result). (b) is faster and also makes the "next round starts immediately" requirement free, at the cost of trusting the client with the answer key, which is harmless for a personal trainer.
- Whether a wrong move is *prevented* (restrict `dests` to repertoire moves, so the learner cannot play it) or *accepted then flashed* (full legal `dests`, then snapback/`set({fen})`) is a pedagogy decision, not a stack one; both board libraries support both.
- Licence: chessground's GPL requirement to publish the site's source is only a problem if the trainer is ever hosted as a closed service. python-chess is also GPL-3.0+, so a hosted closed-source deployment is already constrained by the server side; for a personal/open tool neither matters. cm-chessboard avoids the question on the client.
- Hedged recommendation: **FastAPI + cm-chessboard (ESM from CDN, no build step) + chess.js, one WebSocket per session, python-chess for the repertoire/PGN side**; this is the smallest stack that satisfies the loop. If the rest of the app (progress views, repertoire picker, settings) grows past a couple of pages, **NiceGUI wrapping the same JS board component** is the credible alternative because it keeps FastAPI underneath and reuses the JS unchanged. Reflex, Streamlit and Panel are not recommended for this loop; HTMX + `chess.svg` is a reasonable *first prototype* for local use (the render cost is negligible) but should not be the v1 architecture because it has no drag input and pays an RTT per click.
- Open item for the spec: whether v1 is local-only (any option works, single async worker) or hosted (favours the client-held-branch loop and rules out Streamlit).
