# Opening explanations: can the text Lichess shows on its opening pages be used, and how?

Ticket: [.scratch/chessop/issues/14-lichess-opening-explanations.md](../../.scratch/chessop/issues/14-lichess-opening-explanations.md). Sources are downloaded under [`refs/openings-text/`](../../refs/openings-text/) (index in [`refs/README.md`](../../refs/README.md)); every number in "Coverage" is measured by [`refs/openings-text/coverage-analysis.py`](../../refs/openings-text/coverage-analysis.py) and its verbatim output is [`refs/openings-text/coverage-stats.txt`](../../refs/openings-text/coverage-stats.txt). Measured 2026-09-12.

## Verdict

- **Two texts, not one.** The prose on `https://lichess.org/opening/<name>` is **Lichess's own**, written by Lichess users with an `OpeningWiki` permission and stored as Markdown revisions in Lichess's MongoDB (`modules/opening/src/main/OpeningWiki.scala`). It carries **no published licence** and has **no API**, so it cannot be reused. Only when Lichess has no description of its own does the browser fetch the **Wikibooks "Chess Opening Theory"** page for the move sequence (`ui/opening/src/wiki.ts`), which is also what the analysis board shows in its "Wikibooks" box. The reusable text is the Wikibooks book.
- **Licence: CC BY-SA 4.0** (en.wikibooks `siteinfo.rightsinfo`; `Wikibooks:Copyrights`; page footer), dual-licensed GFDL where no CC-only text was imported. It **can be bundled** in the snapshot as a separate data file next to the CC0 openings list inside the GPL-3.0-or-later app: the text is not a derivative of the program and the program is not a derivative of the text, so neither licence reaches the other; the obligations are a **licence notice, a link to each Wikibooks page used (this is the attribution the Terms of Use accept), and a statement that the text was trimmed**. If the text were ever *rewritten into* the program's own source it would have to go out as GPLv3 (CC declared GPLv3 one-way compatible with BY-SA 4.0 on 2015-10-08), so keep it as data.
- **Fetch:** MediaWiki action API, `https://en.wikibooks.org/w/api.php`, no auth for reads, title `Chess Opening Theory/1. e4/1...c5/2. Nf3` (Lichess's exact rule, below). Wikitext for the whole book is **52 requests** (50 titles each, 2,563 pages, ~4.6 MB); Lichess-style whole-page HTML extracts are **one request per page**. A descriptive `User-Agent` with contact is mandatory (403 otherwise), requests in series, `maxlag=5`; the robot policy's ceiling for unauthenticated clients is 5 req/s. There is also the `enwikibooks-latest-pages-articles.xml.bz2` dump (203 MB, 2026-09-01). Lichess exposes none of this through its API. Once pulled at snapshot-build time the text is static: fully offline afterwards (ADR 0002).
- **Coverage:** the book has **2,563 pages + 464 redirects** under `Chess Opening Theory/`. **Repertoire (`prototype/play-loop/tree.json`, 288 non-root nodes): 208 (72.2%) have a page** (16 of them via a transposition redirect), **175 (60.8%) with ≥ 200 characters of prose**, and every node has such a text at itself or an ancestor. **chess-openings TSV (3,810 lines): 944 (24.8%) have a page, 762 (20.0%) with ≥ 200 characters**; coverage falls with depth (98/156 at ply 3, 47/303 at ply 9, 0 beyond ply 22) and is best in ECO C (324/1,250 lines with prose) and worst in E (28/357). Texts on the repertoire's pages are median ~870 characters (q1 360, q3 2,060). Pages exist **per move order**; positions reached by another order are served only where the book has a redirect (464 exist, 463 pointing at a page).
- **Alternatives:** nothing better. Wikipedia is the same licence but one article per opening family (not per move sequence: `Najdorf Variation` is a redirect into `Sicilian Defence`, 80 KB); the CC0 chess-openings TSV has names only; ECO is a proprietary classification with no free descriptions; Lichess's in-house descriptions have neither licence nor API.

## 1. What the text is and where it comes from

### 1a. Lichess's own opening wiki (the text on `/opening/<name>`)

- The opening page is assembled server-side by `OpeningApi.apply`: `query.closestOpening.traverse(wikiApi.apply)` fetches an `OpeningWiki` for the closest named opening and renders its `markup` into `div.opening__wiki__markup` (`lila-OpeningApi.scala`, `lila-ui-WikiUi.scala`).
- `OpeningWikiApi` reads and writes a MongoDB collection: `write(op, text, by)` pushes a `Revision(Markdown(text), by, at)` (30 kept), the form allows 10–10,000 characters, and editors need the `OpeningWiki` permission (`Granter.opt(_.OpeningWiki)`); it also stores an explorer-derived `popularity` and lists "popular openings with short wiki" (< 300 bytes) for editors to fill (`lila-OpeningWiki.scala`). The route is `POST /opening/wiki/:key/:moves` (`lila-routes-opening.txt`). The file's history starts 2022-10-03 "opening wiki wip".
- Evidence it is not Wikibooks text: the served Sicilian page reads "Black opts for the Sicilian Defense. c5 move stops white from maximizing their control of the center with d4…" (`lichess-opening-Sicilian_Defense.html`), whereas the Wikibooks page reads "1...c5 is the Sicilian defence, a counter-attacking, asymmetric opening…" (`wikibooks-sample-1e4-c5.wikitext`).
- Licence of this text: none is stated on the page or in the UI source (`lila-ui-WikiUi.scala` has only "Edit the description" and the placeholder). lila's `COPYING.md` is the AGPL for the code and says nothing about database content. Treat it as all-rights-reserved.

### 1b. The Wikibooks fallback (the text when Lichess has none, and on the analysis board)

- When no description exists the server renders `div.opening__wiki__markup__placeholder` "No description of the opening, yet." (`lila-ui-WikiUi.scala`; seen live on `lichess-opening-Amar_Opening.html`), and the client script `ui/opening/src/wiki.ts` fills it from Wikibooks (commit 083e6152a0, 2022-12-29 "load wikibooks text on opening pages lacking a description"). The analysis board has done the same since commit d533767784, 2021-10-06 "analysis wikibooks theory POC" (`ui/analyse/src/wiki.ts`), in a toggle box. The page's CSP `connect-src` includes `wikibooks.org` for this.
- **Mapping from a move sequence to a page title** (`lila-ui-opening-wiki.ts`, identical in `lila-ui-analyse-wiki.ts`): for ply `i` with SAN `s`, part = `⌊(i+1)/2⌋._s` for White (odd ply) and `⌊(i+1)/2⌋...s` for Black; join with `/`; delete every `+ ! # ?`; title = `Chess_Opening_Theory/` + path. Skip if more than 30 plies or the path exceeds 234 characters. Example: `e4 c5 Nf3` → `Chess_Opening_Theory/1._e4/1...c5/2._Nf3`. The `sans` come from the page data (the opening's TSV `pgn` plus any extra moves in the URL), so the mapping is by **move order**, not by name and not by position.
- **The request** (`lila-ui-lib-wikiBooks.ts`): `GET https://en.wikibooks.org/w/api.php?titles=<title>&redirects&origin=*&action=query&prop=extracts&formatversion=2&format=json&stable=1`, one page per call; the browser sends it directly (`origin=*` enables CORS). Wikibooks answers `Unrecognized parameter: stable` (`wikibooks-api-sample-1e4-c5-extract-lichess-args.json`), so the `stable=1` added in commit 69bfaa48e5 is ignored.
- **The rendering** (`transformWikiHtml`): from the HTML extract it removes the `<h1>`, the "Theory table" section, the "All possible Black's moves" / "All possible replies" sections, "External links", empty paragraphs and the line "When contributing to this Wikibook, please follow the Conventions for organization.", then appends "Read more on WikiBooks" linking to the page. That link is Lichess's attribution.
- Since 2021-10-31 (commit 2b826bec21) the call passes `redirects`, so a move order that the book redirects to another order shows the target page. The book itself documents this limit: "Lichess looks up pages by move order (not by FEN…) and only supports transpositions if there is a redirect for that move order already in the wikibook" (`wikibooks-Chess_Opening_Theory--How_to_navigate_this_wikibook.wikitext`).

### 1c. The book

- "Chess Opening Theory" on English Wikibooks: "Each page … corresponds to one position in a game of chess. … The title of each page encodes the move order needed to reach that position" (How to navigate). Pages start with the `{{Chess Opening Theory/Position}}` template (name, ECO range, parent, list of responses); the template derives the FEN from the page name with Lua and renders it collapsed so a position can be found with the search box (`wikibooks-Template-Chess_Position.wikitext`); then a heading `== 1...c5 · Sicilian defence ==`, prose, often a "Theory table" and "All possible replies", references, and a navigation footer (`wikibooks-sample-1e4-c5.wikitext`, `wikibooks-sample-1e4-c5.html`).
- Size and activity: 2,563 pages and 464 redirects with the prefix (`list=allpages`); pages by ply 30 / 117 / 161 / 219 / 226 / 266 / 216 / 189 / 169 / 162 at plies 1–10, thinning to 1 at ply 30; median page 1,084 bytes of wikitext, mean 1,799. Last-edit years: 1,002 pages in 2026, 538 in 2025, 260 in 2024 — it is being actively expanded (the `1. e4/1...c5` page was last edited 2026-03-29; the root page 2026-08-11).
- Tone: instructive prose for club players ("The opening is a race for development…", "White has twenty possible first moves…"), with quotations from Evans and Nimzowitsch and citations (`wikibooks-Chess_Opening_Theory.wikitext`).

## 2. Licence

- **Exact licence.** `meta=siteinfo&siprop=rightsinfo` on en.wikibooks returns `Creative Commons Attribution-Share Alike 4.0`, `https://creativecommons.org/licenses/by-sa/4.0/deed.en` (`wikibooks-api-siteinfo-rightsinfo.json`). Every page footer says "Text is available under the Creative Commons Attribution-ShareAlike License; additional terms may apply" (`wikibooks-sample-1e4-c5-fullpage.html`). `Wikibooks:Copyrights`: "Most of Wikibooks' text is dual licensed under the Creative Commons Attribution-ShareAlike 4.0 International License ("CC BY-SA 4.0") and the GNU Free Documentation License (GFDL) (unversioned, with no invariant sections…). Some text may be only available under CC-BY-SA…" (`wikibooks-Copyrights.wikitext`). The Wikimedia Terms of Use section 7 is the binding statement (`wikimedia-Terms_of_Use.wikitext`).
- **Attribution required** (ToU 7, "Re-use": "you agree to attribute the authors in any of the following fashions"): (a) a hyperlink or URL to the page reused, "since each page has a history page that lists all contributors", or (b) a link to a stable free copy that credits the authors equivalently, or (c) a list of all authors. `Wikibooks:Copyrights` adds: "Each copy or modified version that you distribute must include a licensing notice stating that the work is released under CC-BY-SA and either a) a hyperlink or URL to the text of the license or b) a copy of the license. … a suitable URL is https://creativecommons.org/licenses/by-sa/4.0/deed.en". The legal code (§3(a)(1), `cc-by-sa-4.0-legalcode.txt`) lists the same elements plus "indicate if You modified the Licensed Material and retain an indication of any previous modifications". Trimming sections (as Lichess does) is a modification to indicate.
- **Share-alike** (§3(b)): applies to *Adapted Material* only; a copy, excerpt or collection of unmodified text is not adapted, so bundling the text as data imposes no licence on the surrounding program. `Wikibooks:Copyrights`: "If you make modifications or additions to the page you re-use, you must license them under the Creative Commons Attribution-Share-Alike License 4.0 or later."
- **Inside a GPL-3.0-or-later app (ADR 0004).** The relevant compatibility facts: Creative Commons declared "GNU General Public License version 3 … a 'BY-SA–Compatible License' for version 4.0 on 8 October 2015. Note that compatibility with the GPLv3 is one-way only" (`cc-compatible-licenses.html`, analysis in `cc-wiki-ShareAlike_compatibility_GPLv3.html`); GNU: "CC BY-SA 4.0 is one-way compatible with the GNU GPL version 3 … you can not license your adapted CC BY-SA works under the terms of 'GNU GPL version 3, or (at your option) any later version'" unless Creative Commons is named as the §14 proxy (`gnu-license-list.html`, `#ccbysa`). Consequences: (1) shipping the text as a **separate data file under CC BY-SA 4.0** alongside GPL code is plain aggregation; the program stays GPL-3.0-or-later and the text stays CC BY-SA 4.0 (GPLv3 §5, last paragraph, on aggregates; CC §3(b) reaching adaptations only). (2) Only if someone *adapts* the text and wants to distribute the adaptation *as part of the GPL program's source* would the one-way route apply, and then only to GPLv3 (or with the proxy clause). Keep it as data and this never arises. (3) The CC0 openings list (ADR 0003) is unaffected: CC0 asks nothing and the two are different files.
- **Can it be bundled in the snapshot?** Yes. What must ship with it: a licence notice ("Creative Commons Attribution-ShareAlike 4.0 International", with the URL or a copy of the licence), per-text attribution by URL to the Wikibooks page, and an indication that the text was modified (trimmed). A form that satisfies all three, per shown text: *"Text from the Wikibooks book 'Chess Opening Theory', page https://en.wikibooks.org/wiki/Chess_Opening_Theory/1._e4/1...c5 (contributors in the page history), licensed CC BY-SA 4.0 (https://creativecommons.org/licenses/by-sa/4.0/); sections trimmed."* — plus one copy of the licence text in the package. The snapshot file itself must not be relicensed as anything else; a snapshot that mixes the CC0 tree and the CC BY-SA text should say which parts are which.
- Two caveats from the sources: some pages may include short quotations under fair use ("this 'fair use' content does not fall under the CC-BY-SA", `Wikibooks:Copyrights`) — the root page quotes Evans and Nimzowitsch; and the Terms of Use say imported text may carry "additional attribution requirements" shown as page notations, which reusers must preserve. Neither was seen on the opening pages sampled.

## 3. How to fetch it

- **API.** `https://en.wikibooks.org/w/api.php`, MediaWiki 1.47 (`wikibooks-api-siteinfo-rightsinfo.json`); reads need no token. Titles use the book's own form `Chess Opening Theory/1. e4/1...c5` (spaces or underscores). `redirects=1` follows the transposition redirects (`wikibooks-api-transposition-redirects.json`: `1. Nf3/1...Nf6/2. d4` → `1. d4/1...Nf6/2. Nf3`; `1. d4/1...e6/2. c4/2...d5/3. Nc3/3...Nf6` → the `1...d5/2...e6` order).
- **Formats measured.**
  - *Wikitext*: `prop=revisions&rvslots=main&rvprop=content|timestamp|size`, up to 50 titles per request; the whole book (2,563 pages) took 52 requests and is ~4.6 MB raw (`wikibooks-Chess_Opening_Theory-pages.json.gz`). Templates (position header, boards, theory tables, refs) have to be stripped locally; `coverage-analysis.py` shows a workable stripping.
  - *Parsed HTML*: `action=parse&page=…&prop=text`, one page per request, everything expanded — 175 KB for `1. e4/1...c5` including board SVG tables and the theory table (`wikibooks-sample-1e4-c5.html`).
  - *Extract* (what Lichess shows): `prop=extracts` (TextExtracts). HTML by default, `explaintext=1` for plain text with `== headings ==`, `exintro=1` for the lead only, `exchars` ≤ 1,200, `exsentences` ≤ 10 (documented as unreliable). `exlimit` max 20 but **whole-page extracts are limited to one per request** ("exlimit was too large for a whole article extracts request, lowered to 1"); the multi-title limit applies to intros only (`mediawiki-Extension-TextExtracts.wikitext`, paraminfo). The extract for `1. e4/1...c5` is 10.6 KB of HTML (`wikibooks-api-sample-1e4-c5-extract-lichess-args.json`); the ply-10 Najdorf page gives 5.1 KB of plain text (`wikibooks-api-sample-najdorf-extract-plaintext.json`).
  - *Inventory*: `list=allpages&apprefix=Chess Opening Theory/&aplimit=500` with `apfilterredir=nonredirects|redirects`, 7 requests each (`wikibooks-api-allpages-Chess_Opening_Theory.json`).
- **Etiquette and limits** (`mediawiki-API-Etiquette.wikitext`): "There is no hard speed limit on read requests, but be considerate"; "Make your requests in series rather than in parallel"; set `maxlag` (e.g. 5) for non-interactive jobs and back off on a `maxlag` error; "Set an informative User-Agent string with contact information, or you may be IP-blocked without notice". The User-Agent policy makes it mandatory: no or generic UA (e.g. `python-requests/x`) gets HTTP 403 (`wikimedia-User-Agent_policy.wikitext`); format `clientname/version (contact) library/version`. The robot policy (`wikitech-Robot_policy.wikitext`): "Consider if dumps are more efficient than live requests"; unauthenticated clients keep concurrency ≤ 3 and < 5 requests/s; ≤ 10 concurrent and < 20 req/s overall for anyone. This ticket's ~600 serial requests at 0.5–1 s spacing ran without any throttling.
- **Dump.** `https://dumps.wikimedia.org/enwikibooks/latest/enwikibooks-latest-pages-articles.xml.bz2`, 203,255,444 bytes, dated 2026-09-01 (`dumps-enwikibooks-latest.html`): wikitext of the whole English Wikibooks, so the book must be filtered out by title prefix and templates stripped; no HTML. For a snapshot build the API is simpler: 52 wikitext requests, or ~2,600 one-per-page extract requests (~45 min at 1 req/s) if the pre-rendered HTML/plain-text form is wanted, or ~130 requests for intros only. Either way it runs once at build time (ADR 0003, `build-snapshot`) and the text is then static, so the app stays offline (ADR 0002).
- **Lichess's API does not expose it.** The lichess-org/api spec tags are account, analysis, …, openingexplorer, puzzles, … — no opening-text tag; the local spec has only the four explorer paths, and the explorer's `opening` object is `{eco, name}` (`refs/lichess/openapi-schema-OpeningExplorerOpening.yaml`). lila's `/opening/*` routes are HTML pages only (`lila-routes-opening.txt`). The in-house descriptions could only be scraped from `div.opening__wiki__markup`, and have no licence (§1a).

## 4. Coverage

Method: titles built with Lichess's rule (§1b); existence decided from the `allpages` inventory; redirect targets resolved with `redirects=1`; "prose" = wikitext with templates, tables, refs, headings, links and the sections Lichess hides removed, whitespace collapsed; "real prose" threshold 200 characters (about two sentences), 500 also reported. Lichess-style HTML extracts, put through a port of `transformWikiHtml`, were fetched for every matched repertoire page (197) and 60 sampled TSV pages to calibrate: the extract text is 1.14× the local prose measure at the median (q1 1.08, q3 1.31) and the ≥ 200 verdict agrees on 251 of 277 pages, so the local numbers slightly **understate** what Lichess would show. Full per-line and per-node tables: `coverage-lines.tsv`, `coverage-tree.tsv`.

- **The book overall:** 2,563 pages; prose per page min 0, q1 132, median 325, q3 806, max 46,497 characters; 2,075 pages ≥ 100, **1,640 (64%) ≥ 200**, 986 ≥ 500, 498 ≥ 1,000, 164 ≥ 2,000. 167 pages have no prose at all (only the position template and a moves list).
- **chess-openings TSV, 3,810 named lines:** 930 have a page at the TSV's own move order and 14 more via a redirect: **944 (24.8%) any page; 762 (20.0%) with ≥ 200 characters; 551 (14.5%) with ≥ 500**. Among the pages hit, prose is q1 253, median 646, q3 1,275 characters. One line (36 plies) exceeds Lichess's 30-ply cap. By ply (lines / any page / ≥ 200): 1: 20/20/20; 2: 93/66/59; 3: 156/98/87; 4: 227/112/81; 5: 293/114/95; 6: 357/132/106; 7: 308/91/73; 8: 304/73/61; 9: 303/47/35; 10: 276/54/42; 12: 242/28/22; 15: 119/11/8; 18: 67/5/5; nothing from ply 24 on. By ECO volume (lines / ≥ 200): A 817/136, B 772/191, C 1,250/324, D 614/83, E 357/28. The missing lines are dominated by rare gambits and sidelines (the first twenty at ply ≤ 6 are all `A00` Amar/Barnes/Grob/Hungarian lines) and by anything deep.
- **Repertoire, `prototype/play-loop/tree.json`:** the file has 289 nodes (5,017 games, cut-off 0.2%, width 3, max ply 18), so 288 non-root positions — not the 235 of ticket 05's measurement, which came from a different month/band build; the numbers below are for the file as it is. **208 nodes (72.2%) have a page** (192 directly, 16 through a transposition redirect), **175 (60.8%) have ≥ 200 characters**, 134 (46.5%) ≥ 500; prose on the pages hit is q1 360, median 866, q3 2,063, max 12,041 characters (Lichess-style extract: q1 436, median 899, q3 1,806). Of the 175 nodes that carry a TSV name (`named_here`), 158 have a page and 139 have ≥ 200 characters. Of the 94 leaves, 53 have a page and 40 have ≥ 200. **Every one of the 288 nodes has ≥ 200 characters at itself or an ancestor**, so "walk back to the nearest page" (the same rule the TSV names use, ticket 12) names a text for every drilled position. By ply (nodes / any page / ≥ 200): 1: 3/3/3; 2: 9/8/8; 3: 24/20/19; 4: 37/31/25; 5: 46/35/32; 6: 44/30/28; 7: 40/27/21; 8: 30/16/11; 9: 19/10/8; 10: 14/10/6; 11: 7/4/2; 12: 5/4/3; 13–18: 10/10/9. The main-line pages are substantial: `e4` 6,364, `e4 c5` 8,562, Najdorf 4,707, Rossolimo 4,128, Accelerated Dragon 3,459 characters; the ply-10/11 Accelerated Dragon `Bg7`/`Be3` pages have only ~60 characters (a one-liner before a moves list). Whole missing sub-trees exist: e.g. `e4 c5 Nf3 Nc6 Bc4` and its two replies.
- **Positions versus move orders (ticket 11).** Pages are keyed by move order; the book's answer to transpositions is redirects (464, 463 of them pointing at an existing page) plus FEN full-text search for humans. 14 TSV lines and 16 repertoire nodes get their page only through a redirect, so an app that looks up by the TSV's `pgn` without `redirects=1` loses them. A lookup by position is possible only indirectly: the rendered page contains the FEN (Lua-derived), so `list=search` on the FEN's first field would find pages for a position under any move order, but this was not measured and is not what Lichess does.
- **Lengths.** For a drilled position the typical text is about 900 characters (roughly 150 words) once the theory table and moves lists are cut; a quarter of the matched pages exceed 2,000 characters and the family root pages run to 6–9 KB. Texts are written per position ("1...c5 is the Sicilian defence…", "Black plays 5...a6 and controls the b5 square…"), so a page at a node reads as an explanation of that node, and its `responses` list matches the tree's children.

## 5. Alternatives

- **Wikipedia (en).** Same licence, CC BY-SA 4.0 (`wikipedia-api-rightsinfo-and-opening-articles.json`). One encyclopaedic article per opening *family* — `Sicilian Defence` is 79,930 bytes, but `Najdorf Variation` is a 61-byte redirect into it — so there is no per-move-sequence text and mapping a TSV line or tree node to a paragraph would need hand work; the writing is historical/encyclopaedic rather than instructive. Not a better fit; possibly a supplement at family level.
- **ECO / chess-openings.** The CC0 TSV carries `eco`, `name`, `pgn` only (`refs/lichess/chess-openings-README.md`); the Encyclopaedia of Chess Openings itself (Chess Informant) is a proprietary classification and publishes no free descriptions. Nothing to reuse.
- **Lichess's own descriptions.** Better matched to Lichess's opening keys (they are written per `OpeningKey`) and shorter, but no licence, no API, editable only by permission holders. Unusable.
- **Other wikibooks.** The "Chess Opening Theory" book is the only per-position free text found; Wikibooks' other chess books (`Chess`, `Chess Strategy`) cover principles, not lines.

Conclusion on fit: the Wikibooks book is the only freely licensed source organised the way the drill is (one text per move sequence, per side to move, with a responses list), it is the very text Lichess falls back to, and its coverage of the repertoire's main lines is good (72% of nodes, 100% with ancestor fallback) even though its coverage of the full TSV is a quarter.
