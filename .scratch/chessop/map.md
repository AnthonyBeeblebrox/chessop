# Map: Chess opening trainer by sampling

Labels: wayfinder:map
Source idea: [prompt0.md](../../prompt0.md)

## Destination

A **build-ready spec** for a Python web app that drills the learner on main chess openings through fast, sampled play: `.scratch/chessop/spec.md`, backed by a settled glossary (`CONTEXT.md`) and ADRs for the sampling rule, the opening-tree data source, and the web/board stack. Done when a coding agent could implement v1 with no design decision left open, and the literature on learning openings sits in `refs/` with a findings summary. Single learner, local-first.

## Notes

- **Domain**: chess opening training, spaced repetition / adaptive sampling. Learner plays one side against an "opponent" whose replies are sampled from the opening tree; each visit to a branch is scored as a success or failure; success lowers that branch's sampling weight without ever zeroing it.
- **Standing preferences** (from prompt0.md): Python; web app; speed first ("the user sees a maximum of games"); Lichess API / SDK / database as the data source; literature material downloaded into `refs/`.
- **Charting caveat** (discharged): the destination and scope above were the agent's reading of prompt0.md until ticket 05 grilled and confirmed them, adding *single learner, local-first*.
- **Skills every session should consult**: `grilling` + `domain-modeling` for every HITL ticket; `research` for research tickets; `prototype` for prototype tickets. Domain vocabulary lives in `CONTEXT.md` — the repertoire vocabulary is settled by ticket 05, the memory vocabulary (Pass, Miss, Position record, Recall estimate, Half-life, Need, Floor, Forced exploration, Sampling weight) by ticket 06; the sampling rule is ADR 0001; persistence, deployment shape and the global scope of history are ADR 0002 (ticket 07); the opening-tree snapshot (source, bands, filters, storage, refresh) is ADR 0003 (ticket 08); the web stack (framework, board, socket protocol, latency budget, packaging) is ADR 0004 (ticket 09); the play-page feel (no mid-round reveal, arrows at round end, Space for next, forced exploration announced) is ticket 10; the repertoire rule (book-terminated depth, top-3 plus 5 % share width, 0.02 % floor, stubs, whole-book default scope) is ADR 0005 (ticket 13), which supersedes ticket 05's cut-off and adds Book to the glossary; the position graph (EPD-keyed DAG, pooled counts, one record per position, canonical order, name along the path, opt-out by exact name) is ADR 0006 (ticket 11), which corrects ADR 0001's record key and amends ADR 0003 and 0005 and adds Position to the glossary; The spec itself is `.scratch/chessop/spec.md` (ticket 20): read it first, it points at everything above.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->
- [Literature: how do people learn chess openings, and what does the evidence say works?](issues/01-literature-learning-openings.md): experts store openings as positions (templates), not move strings; no chess-specific spacing study exists, so fit intervals from own data; never drop a known branch (one-success dropping cuts recall 80% to 33%); weight by predicted recall (failures + elapsed time) not failure count, target ~80-90% success; success = first-try whole branch, post-reveal replays never count; key by position for transpositions. See docs/research/learning-openings.md.
- [Algorithms: how should a branch's sampling probability decay with its success count?](issues/04-sampling-scheduling-algorithms.md): weight = popularity(path) * (eps + 1 - R), with Leitner/HLR R = 2^(-delta/h), h = h0*2^(s-f) clipped so nothing hits zero; compose by subtree sums so each leaf is drawn with prob w/W(root) and updates are O(depth); FSRS/ACT-R are drop-in need models; rule to be settled in ticket 06.
- [Stack: which Python web stack gives a fast interactive board with the least friction?](issues/03-python-web-board-stack.md): FastAPI + cm-chessboard (MIT) + chess.js over one WebSocket per session, python-chess server-side; the fast loop is client-side JS in every option, NiceGUI is the Python-first fallback, chessground is GPL, Reflex/Streamlit/Panel and HTMX+chess.svg lose on latency or friction.
- [Lichess data: which API / dataset gives us the main-opening tree with move frequencies?](issues/02-lichess-data-sources.md): explorer API is the only direct per-move-popularity source but needs an OAuth token (25 req/min, 50 plies) since Mar 2026; build the sampling tree offline from a CC0 dump month (≥0.2–1 % cut-off ≈ 60–450 nodes, 6–18 plies by rating band), name nodes from the CC0 chess-openings TSV, use the explorer only to refresh/seed.
- [Destination and repertoire: what counts as a 'main opening', how deep, and for which side?](issues/05-confirm-destination-and-repertoire.md): destination confirmed plus single learner / local-first; repertoire = the main lines at the learner's own rating band by an **absolute** cut-off of ≥0.2 % of that band's games (ply 18, nine moves each; 235 positions), grouped by ECO family and scoped by the learner; both colours in one repertoire with the app sampling the side; Branch = full path and the success unit; any of the top P moves is accepted, only `max(P,O)` sizes the tree (default (3,3), (1,3) as strict recall); moves hidden while playing, revealed after, hard-restart on a miss; epsilon discards the learner's best-known move. See docs/research/tree-width-measurements.md.
- [Transpositions: how many positions in the repertoire are reachable by more than one move order?](issues/12-transposition-prevalence.md): at 1800+ / 0.2% / (3,3), 17 of 216 positions (7.9%) are reached by >1 move order, 36 of 235 nodes (15.3%), and 41% of leaf paths pass through one; they sit at plies 3-8 only (first at ply 3), largest group 3 orders (4 uncapped), all `d4`/`e4 e6`/`e4 c5` families; merging by position shrinks the tree 8% but 14 of 17 groups keep different replies per move order, so a sequence tree drills the same position inconsistently; side to move is in the EPD and no group spans plies, so the key needs the learner's colour only because both colours are drilled on one tree; chess-openings `epd` is a usable key (3,810 distinct, 0 mismatches), naming 67.7% of nodes exactly and every node via a named ancestor; other bands have 2-4% shared positions. See docs/research/transpositions.md.
- [Success rule: what does 'successfully played the branch' mean, and how does success shape sampling?](issues/06-success-rule-and-sampling.md): history is kept per position and per learner colour, not per branch — a round is a playout, each position got right takes a pass, the one missed takes a miss (ancestors keep their passes); half-life recall model (pass doubles, miss halves, clock runs from the last pass, never-passed = 0), need = max(floor 0.1, 1 − R); a pass counts only when R < 0.9 and the first pass after a miss is an uncounted relearning pass, a miss always counts; opponent draws a move by popularity × popularity-weighted mean need below it + Boltzmann-Gumbel exploration bonus, popularity renormalised over kept moves; side drawn by total need with a 0.2 floor; forced exploration 0.1 discards the lowest-need main move; no cap on new material; every round logged for refitting; target 80-90 % success monitored only. ADR 0001, docs/adr/0001-sampling-rule.md.
- [Users and persistence: single local learner or accounts, and where do branch stats live?](issues/07-users-and-persistence.md): no accounts, login or learner id (a second person uses another data directory); one SQLite file in the XDG data dir holds position records, round log and settings; history is global per position and colour and survives every repertoire regeneration, deleted only by an explicit reset; server authoritative with write-through at every round end, thin tabs serialised; no Lichess token in v1, fully offline from the snapshot; deployment is one command starting a localhost server that opens the browser, LAN bind by flag; backup is copying the file. ADR 0002, docs/adr/0002-persistence.md.
- [Data source: live Lichess explorer calls, an offline snapshot, or the ECO TSV?](issues/08-data-source-decision.md): a snapshot built by the developer from one recent whole month of the CC0 dump and shipped as package data, never learner-built and never live; five fixed 300-wide bands (both players inside), bullet and bots excluded; per band the sequence trie with count, EPD and TSV name per node, stored at 0.02 % and never pre-merged, the 0.2 % repertoire cut-off applied at load from settings; a separate read-only versioned file, the learner's SQLite recording only the version used; refresh release-only, with a `build-snapshot` CLI and a `--snapshot` override; the runtime never reads the TSV or the network. ADR 0003, docs/adr/0003-opening-tree-snapshot.md.
- [Stack: which web framework and board library, given the speed-first play loop?](issues/09-stack-decision.md): FastAPI with Jinja2 pages and one JS module on the play page, no client framework or Node; chessground (Lichess board) vendored with Lichess defaults, project GPL-3.0-or-later as python-chess already required; no chess logic in the browser, the server sends FEN plus legal dests and judges any legal move; one WebSocket per tab with `move`/`next` up and `round`/`moved`/`round_over` down, the client asking for the next round; one round per tab with round-end commits under a lock, a dropped socket abandons the round; auto-queen; budget: move handled < 10 ms, reply visible < 100 ms, next round < 200 ms, animation ≤ 100 ms; uv project, Python ≥ 3.12, `chessop` serves localhost:8000 and opens the browser; pytest plus the FastAPI test client over the socket, no browser tests. ADR 0004, docs/adr/0004-web-stack.md.
- [Play loop: what does one fast round look and feel like?](issues/10-play-loop-prototype.md): no reveal while playing, only the banner (colour badge, orientation, opening name); when the round ends the main moves are drawn as green arrows on the board with the played move red and a one-line verdict under the board; next round on Space after every outcome, no timer; forced exploration is announced as a yellow arrow on the board before the learner moves plus the banner, fires only when one main move is strictly better known, and playing the set-aside move ends the round as neither pass nor miss (ADR 0001 amended); pass kind and recall numbers stay off the play page; wire gains a `forced` verdict/outcome and an empty `dests` on a round-ending `moved`. Prototype in prototype/play-loop/ (variant C won).
- [Repertoire rule: every named variation in the book, or only lines that survive a popularity cut-off?](issues/13-repertoire-named-variations.md): the book (the `chess-openings` list) sets depth and popularity sets width — at load keep the main moves (top-3 plus any reply with ≥ 5 % of the games reaching the position) that clear a 0.02 % floor, then prune every node with nothing named at or below it, so a branch ends at its deepest name; whole book in by default with family opt-out; no-traffic named lines out; a main move with nothing named below is a stub, accepted for the learner and never drawn by the opponent; snapshot ply cap to 36 and names flagged exact; 389 lines / 996 positions / 17 plies at 1800–2100 on August 2026 data (old rule 69 / 173 / 10). ADR 0005; 195 book lines lost to transposition handed to ticket 11. See docs/research/repertoire-rule-candidates-recent.md.
- [Transpositions: is a branch a move sequence or a position, and how does success credit a position reached another way?](issues/11-transpositions.md): the repertoire is a DAG of positions keyed by EPD with counts pooled over move orders, built by `build-snapshot` (the snapshot stores positions and edges, not a trie), on which ADR 0005's rule runs unchanged, recovering the 195 transposition-only book lines; one position record per position with full credit whatever order reached it, colour being the side to move inside the EPD (ADR 0001's two-records-per-colour corrected); a Branch is one path, a leaf still the deepest named position; cycle-closing edges dropped at build; only exact names stored, the banner inherits along the path walked; a canonical most-popular move order per position for the progress view and the wikibook lookup; opting an opening out removes its exactly-named positions and re-runs the prune; one reveal per position. ADR 0006, docs/adr/0006-position-graph.md; size measured by ticket 17.
- [Pooled repertoire: how big is the position graph ADR 0006 builds, and does pooling admit junk?](issues/17-pooled-repertoire-size.md): on ticket 13's 2026-08 sample at 1800-2100 the pooled graph is 1,104 positions / 1,326 edges / 1,985 branches / 310 leaves / 17 plies (the sequence tree's 996 nodes were 772 distinct positions, all kept, plus 332 recovered), covering 662 of the 996 named lines with traffic (535 before; 108 of the 195 transposition-only lines back, 87 still out, `1.Nf3` still rank 4 at 3.7 %); 0 cycle edges dropped; 86 positions where no single order holds 25 % of the pooled count, 70 of them entered only by moves main under no single order, 234 such edges of 1,326; 60 % of positions exactly named, 159 unnamed ones inherit more than one name, canonical order differs from the book's line for 107 of 662; 546 White-to-move / 558 Black-to-move. See docs/research/pooled-repertoire.md.
- [Opening explanations: can the text Lichess shows on its opening pages be used, and how?](issues/14-lichess-opening-explanations.md): the text on Lichess's opening pages is Lichess's own unlicensed user wiki (no API), but its fallback and the analysis board use the Wikibooks "Chess Opening Theory" book (CC BY-SA 4.0), looked up by move order `Chess_Opening_Theory/1._e4/1...c5`; it can ship in the snapshot as a separate CC BY-SA data file beside the CC0 tree in the GPL app with a per-page link, a licence notice and a "trimmed" note; fetched from the MediaWiki API (52 batched requests for the whole book, descriptive User-Agent, serial), offline afterwards; covers 72% of repertoire nodes (61% with real prose, 100% via a named ancestor) but only 25% of the 3,810 TSV lines, per move order with redirects for transpositions; no better free source exists. See docs/research/opening-explanations.md.
- [Opening explanations: does the drill show the wikibook text, where, and does it ship in the snapshot?](issues/15-opening-explanations-in-the-drill.md): in v1, called an Explanation; shown at round end under the verdict strip for the revealed position (lead plus a "more" toggle, plain text, Space goes straight on, no setting) and in the progress view, never mid-round; a position without a page borrows the nearest one on the path walked, labelled; `build-snapshot` pulls the wikitext once and ships a separate CC BY-SA 4.0 file beside the CC0 graph for every snapshot position in all bands, looked up by the book's line then the canonical order with redirects; attribution is a per-text footer linking the page, a README notice, a `LICENSES/` copy and a header in the file; `round_over` carries the text. ADR 0003 amended.
- [Gamification: what rewards the learner, and what single score says how well they know their openings?](issues/16-gamification.md): the Score is the popularity-weighted mean recall estimate over the learner positions of the scoped repertoire, i.e. the chance of playing a main move at a random learner turn in a real game; it decays between sessions, one combined number in the banner at one decimal with the per-round change on the verdict strip (none after `forced`) and the change since the last round shown once when a tab opens; colour split and per-opening scores only in the progress view; sounds from Lichess's `sfx` set (AGPLv3+; the default `standard` set is non-free): Move/Capture/Check on every move, Victory on success, Error on a miss, nothing mid-round, on by default with a settings toggle and `m`; streaks, daily goals, milestones and a session summary out of v1, the score history graph left in the progress-view fog. ADR 0001 amended, Score added to the glossary.
- [Progress view: what does the learner see about their repertoire, and how is a position shown?](issues/19-progress-view.md): a ledger, chosen by prototype over a board-first explorer and a heatmap: one server-rendered page of openings in order of the share of games reaching them (score, White/Black split, known/learning/never bar, in/out toggle, reset), each unfolding into its exactly-named lines and then its branches in canonical order with every learner move coloured by recall; one page per position (SVG board, recall estimate, half-life, passes and misses, time since the last pass, share and move orders, a state word with "known" meaning recall ≥ the 0.9 sure threshold, main moves, the explanation, reset); on the head the Score with its change since the last day, the colour scores, the in-session success rate against 80–90 %, a score sparkline and a never-passed count linking to that list by popularity; a daily score table upserted at every round-end commit (ADR 0002 amended); opt-in/out and finer resets live here, "drill from here" out of v1; no second JS module (ADR 0004 amended). Prototype in prototype/progress-view/ (variant A won).
- [Pooled-only main moves: keep every edge that clears the floor only as a sum of orders, or require one order to clear it?](issues/18-pooled-only-main-moves.md): keep them; a position's traffic is its pooled traffic over every move order, so the popularity floor, top-3 rank and 5 % share apply to pooled counts with no per-order rule, since the edges main under no single order are largely the lines ADR 0006 recovers (the Semi-Slav Main Line: 215 games over 102 orders, none above 13) and ADR 0005 never scores a move real players make as a miss; the 1500-1800 losses (French Tarrasch, Rousseau) are 5 % threshold cases, accepted; "junk" renamed diffuse traffic, reported by `build-snapshot` per band as a diagnostic; ADR 0005's 996 positions restated as 772 (pooled graph 1,104); glossary gains Popularity floor, distinct from the need Floor. ADR 0005 and 0006 amended.

- [Spec: write the build-ready v1 spec from the ADRs and the resolved tickets](issues/20-write-the-spec.md): `spec.md` written, 17 sections in build order, each citing its ADR or ticket with gist and numbers; two contradictions left open (does a mid-round `moved` carry the reveal, ADR 0004 vs ticket 10; which position a success reveals, ticket 10 vs ticket 15) and three undecided details (need aggregation over an empty subtree and whether a moveless leaf is a learner position; forced rounds in the daily and in-session counts; how the `m` sound toggle persists), all handed to ticket 21; the spec's §17 lists the readings it made where sources were silent, each with its source.
- [Spec gaps: the two contradictions and three undecided details ticket 20 found while writing the spec](issues/21-spec-gaps.md): a mid-round `moved` carries no reveal; on a success the arrows show the position the last move was played from (the opponent's, before a reply that ended the round) while the explanation is the leaf's, so the two may differ; an empty subtree's mean need is the floor, and a leaf with the learner to move is not a learner position (no record, out of the Score and the side draw); forced rounds are left out of both the daily and the in-session round and success counts; the `m` toggle persists through a fifth socket message `sound {on}`. Spec §15/§16 rewritten as decisions, ADR 0001 and 0004 amended, glossary Explanation and Position record reworded.
- [Capped month build: the whole-month trie does not fit in memory](issues/22-capped-month-build.md): a whole month is ~1.2 billion trie nodes (~400 GB), so `build-snapshot` reads a capped prefix of the month, at most 150,000 kept games per band (ticket 17's sample size, its numbers stay the sanity bounds, ~6 GB, ~5–6 % of the file); cut-off, filters, bands and files unchanged; cap and bytes read in the metadata; `zstandard` moves to the `chessop[build]` extra (ADR 0003 and spec amended)
- [Exploration bonus: the Gumbel noise swamps popularity, so the no-history opponent is not the database opponent](issues/23-exploration-bonus-inside-the-product.md): `weight = pop^alpha * (mean_need + C / sqrt(1 + faced))`, drawn proportionally, no noise and no clamp; with no history the opponent is exactly the database opponent at any `C`, rarely faced replies still favoured (ADR 0001, spec and glossary amended)
- [Round depth: rounds end too early, where the book stops naming the line](issues/24-round-depth.md): playing v1 the learner found rounds too shallow (about 9 plies at 1500-1800 for a perfect learner); ADR 0005's named-position prune is dropped, so a branch runs until the popularity floor ends it and a leaf need not be named; 1500-1800 grows from 794 positions / 15 plies to 2,695 / 17; deeper still would need a larger snapshot, not taken; the Explanation borrows the nearest text on the path walked as before. ADR 0005 amended; build ticket chessop-v1 16.

## Out of scope

- Middlegame/endgame training and engine analysis of full games: the destination is opening drilling only.
- Multiplayer or playing against other humans: the opponent is always sampled from the opening tree.
- Hosting, multi-device sync, accounts and login: ruled out by ticket 07 (ADR 0002); the app is one local server per learner and the database file is the backup.
- Streaks, daily goals, per-opening milestones and a session summary: ruled out of v1 by ticket 16 (gamification); they schedule by calendar where the app's premise is that the model schedules.
- Seeding from the learner's own Lichess games (importing games to pre-populate position records and pick the openings they actually face, and the token handling it needs): post-v1, ruled out on 2026-09-22 once ticket 19 closed the last v1 decision; ADR 0002 already keeps any token out of v1. The learner's token (`token.txt`, git-ignored) waits for that fresh effort.
- Evaluation of the learning method (retention measurement, capping never-seen material, self-adjusting toward the target success rate, refitting the half-life parameters from the round log): post-v1, ruled out the same day. V1 keeps what it needs: the round log (ADR 0002) and the daily score table (ticket 19) are the data that effort will consume.
